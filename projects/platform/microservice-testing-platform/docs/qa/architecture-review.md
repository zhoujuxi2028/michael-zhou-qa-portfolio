## 2. 关键质疑与回应

| # | 质疑 | 回应 | 状态 |
|---|------|------|------|
| Q1 | 为什么用 Redis Pub/Sub 而非 Kafka/RabbitMQ？ | 单组件解决消息+缓存、依赖少、演示成本低；但 Pub/Sub 是 at-most-once，无持久化 | 已回应，残余风险见 R3 |
| Q2 | 库存扣减为什么用同步 REST 而非异步？ | 下单需立即知道结果（成功/库存不足）才能决定订单状态；异步会引入状态补偿复杂度 | 已回应 |
| Q3 | 幂等如何保证，重复事件会不会重复扣款？ | 支付按 `order_id` 去重、库存按 `order_id + type` 去重，均有单测/集成验证 | 已回应 |
| Q4 | 支付回调失败怎么处理？ | `redis-subscriber` catch 仅记日志，无重试/补偿，订单可能卡 confirmed | **未解决**（残余风险 R4，见 §3） |
| Q5 | 契约测试为什么用 ajv JSON Schema 而非 Pact？ | 零依赖、行为确定可单测、CI 友好；Pact 需 Broker + 额外基础设施 | 已回应 |
| Q6 | 集成测试为什么 mock 外部依赖而非真实 Redis？ | 隔离单服务、快速稳定；真实依赖由 E2E/性能层承担 | 已回应 |
| Q7 | E2E 为什么 mock Redis，能算真正的 E2E 吗？ | 进程内起 inventory + mock Redis，验证核心业务流程但非真实事件流；真实 Redis 事件流在 docker 环境手动演示 | **部分未决**（见 §3） |

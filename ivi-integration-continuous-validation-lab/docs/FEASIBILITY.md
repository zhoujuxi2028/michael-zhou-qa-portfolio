# IVI 软件集成与持续验证实验室 — 可行性评估

**结论：** 作为纯软件模拟实验室可行；真实 ECU/台架联调不在本项目可行性承诺内。实施前需经需求和设计评审。

## 技术选择建议

| 领域 | 建议方案 | 理由 / 限制 |
|---|---|---|
| 语言与测试 | Python + pytest | 适合状态流模拟、测试分层和本地/CI 自动化 |
| 部署模型 | 本地文件包 + 明确状态机 | 无硬件或外部系统依赖，方便故障注入和回滚验证 |
| 执行目标 | `virtual` / `bench-sim` 模拟适配器 | 共用执行接口；bench 名称不得暗示真实台架连接 |
| 日志 | Python `logging` + JSON 行记录 | 易于关联 run ID、阶段和目标；不需先引入日志服务 |
| 报告 | pytest 原始结果 + 项目 HTML 汇总报告 | 保持离线可用；Allure 可作为后续可选适配，不应成为首期运行前提 |
| 并行 | pytest-xdist 作为候选依赖 | 先建立串行基线，再通过依赖评估决定是否引入；比较时记录配置 |
| 环境 | `make ci` + Dockerfile | Make 统一入口，Docker 提供隔离环境；本地入口不能依赖 Docker 才可运行 |
| 持续集成 | 独立 GitHub Actions workflow | 正常流水线验证质量门禁；故障注入示例应隔离在独立 job 或手动触发路径 |

## 关键可行性与约束

- 包完整性可用固定 manifest/hash 样例验证；不生成或处理真实厂商固件。
- 部署与回滚可用版本目录/内存状态模拟。实现需定义提交点，避免失败后产生“部分成功”状态。
- 串行与并行耗时仅对固定工作负载和运行环境有比较意义；结果须带环境、worker 数和样本量，避免宣称普适加速比。
- Flaky rate 需要重复运行；首期可通过确定性故障注入验证采集流程，真实随机波动率需足够样本后再报告。
- 故障构建识别率需要已知的正/负样本矩阵；CI 必须确保故障注入场景验证门禁行为，但不能让预期故障误报为整体流水线失败。
- Docker 可能受平台、镜像下载和权限影响；本地 `make ci` 应保持最小工具链和可用性。

## 依赖决策门

首期优先 Python 标准库与 pytest。实现前分别评估 `pytest-html`/自建 HTML、`pytest-xdist`、Allure 的维护成本、离线可用性和 CI 复杂度；确认具体版本后按仓库要求检查依赖安全性并锁定依赖。当前不添加运行依赖。
